# 0.18.0：open 核对没跑成时干净副本接血统（默认开，可关）+ `file.resolve()` 主动叫冲突面

> created 20261016 by Claude Fable 5.1 · as-of 0.18.0 · user 2026-10-16「库 bump minor 做」「我要的就是本地覆盖云端和云端覆盖本地二选一啊！这个才是安全的模型！」「取消也要」「禁止越狱」；WXHW 会话 10-16 查出的单设备根因（`20260516 WebXiaoHeiWu/ai-docs/20261008-store-0162-signin-push-order-handoff.md` §6.1）。minor（新接口 + 一条默认行为变化）。

## 行为差异（和 0.17.2 比）

| 项 | 0.17.2 | 0.18.0 默认 | 关掉 |
|---|---|---|---|
| open 时云端核对没跑成（离线 / 未登录 / fetchMeta 抛错 / 用户 probe 跳过），本地副本**干净**且磁盘上有上次同步的 etag | 什么都不记 → 本 tab 无 base → 之后第一次 save 的推不带 If-Match → `conflictBehavior:"fail"` → 云端有同名 → 409 → 大小不等 → `CloudNameCollisionError` → 冲突面（云端其实没人动） | **把那个 etag 记为本 tab 的 base**（`head.markSeen`）→ 第一次推带 If-Match：云端没动 → 成功；动过 → 412 → tryHeal / 冲突面（和以前一样） | `createStore({ openLineageFromDurable: false })` |

安全边界：base 只会被记成**本地字节当时同步到的那一版**（durable etag 只在 push 成功 / markSynced 时和字节一起写），永远不会比字节更新 → If-Match 照样挡住真分叉。脏副本一律不动（脏的 parent 只能由 recordEdit 或云端确认过的 markSeen 给；从 durable 补 parent 在多标签页下会变成静默覆盖——**没做，也别做**）。seenBase 的其他消费者（offload 守卫、upload-queue、reconcile、safe-resolve 备份判据、uploadReplay.enqueue）本来就回退到同一个 durable etag，行为不变。

## 新接口

`RawFile.resolve(opts?: { adopt? }): Promise<ResolveOutcome>`——库**自己**弹 `ui.resolveConflict({ occasion: "push" })`，按人选的走既有派发：本地覆盖云端 = 正常 If-Match 推（云端此刻若已变 → 412 → 库再弹面，不预设答案）；云端覆盖本地 = `safePull({ forceBackup: true })`；取消 = 不动。干净的文件返 `clean`。app 只负责调它、**不传答案**。
`ResolveOutcome` = no-local / clean / offline / cancelled / pushed / not-pushed(reason) / took-cloud(backupName) / unresolved(reason)。took-cloud 后 app 必须整份重读。

被否决的替代方案（别再提）：`file.takeCloud()`（app 代码不经面就换字节——哪怕先进备份箱也是越狱）；app 侧预设答案喂 `resolveConflict`（KudsRocket v0.1.33–0.1.35 的 presetResolution，已删）。

## 0.18.2（同日，patch）：冲突面带 `cloudState`；云端没了时「云端覆盖本地」= 本地进回收站

user 2026-10-16：「存档管理里"云端没了/从未上传"这类行目前只有「传上去」一个选项…是UX在逼我，然后为什么这里还是越狱了，这个按钮原则上应该compile error」「因为这个动词一开始就不合法，不在词汇表上」。
词汇表只有三个词：**云端覆盖本地 / 本地覆盖云端 / 取消**，只在库弹的面里出现；app 不许自造「传上去」「推一把」「重新上传」这类方向动词。
- `ui.resolveConflict` 的 ctx 多一个 `cloudState?: "changed" | "absent" | "unchanged"`（宿主措辞用；老宿主不传照旧）。412 / 撞名 / open 时云端更新 = changed；`resolve()` 先 fetchMeta：没了 = absent、etag === base = unchanged。
- `resolve()` 在 **absent** 时选「云端覆盖本地」= 跟着云端：本地这份走库的删除路径进回收站（可恢复），返 `{ status: "trashed" }`；选「本地覆盖云端」= 传回云端。以前这种行在 app 里只有一条「传上去」= 本地权威，被判越狱。
- 测试 `test/resolve.test.ts` 末条（absent → trashed / pushed；unchanged 状态）。458 过。

## 0.18.5（2026-10-17，patch）：`resolve()` 也管「干净 ∧ 同步过 ∧ 云端没了」（列举里的 pendingGone）

> added 20261017 by Claude Opus 5.5

KudsRocket user 2026-10-17：「云端没有的情况点处理没有给选项，然后一直卡着待处理」。那一行的列举状态是 `pendingGone`（这台的副本干净、同步过、云端那份没了，24 h 宽限期内；过了宽限期库自己把本地移进回收站）。
0.18.0 的 `resolve()` 第一步「不脏就回 clean」→ 不弹面，宿主只能说「没有要处理的改动」，行照旧挂着。gallery 的「处理…」对 pendingGone 行同一个洞。

改法：`resolve()` 遇到干净的副本时，**同步过 ∧ 在线** → 问一次云端（fetchMeta）；**云端确认没了** → 面照弹（`cloudState: "absent"`）：
云端覆盖本地 = 这份走库的删除路径进回收站（`trashed`，和 0.18.2 的 absent 分支同一条路）；本地覆盖云端 = `reupload()` 那段首推（不带基准、撞名不覆盖 → 抛给宿主；`pushed` / `not-pushed`）；取消 = 不动（`cancelled`）。
`reupload()` 的函数体提成 `makeRaw` 里的共用函数，逐字未改。

### 行为差异（艺术类 app 升级时逐条过）

1. `resolve()` 对**干净 ∧ 同步过**的文件，在线时多一次 `fetchMeta`（以前零网络直接回 clean）。只在人按「处理…」时发生。
2. 那次 fetchMeta 说云端没了 → **弹面**（以前回 `clean`）。返回值多了 `trashed` / `pushed` / `not-pushed` / `cancelled` 这几种可能——都是 `ResolveOutcome` 里已有的值，类型没变。
3. 干净 ∧ 是 pendingGone candidate ∧（离线 或 fetchMeta 抛错）→ `offline`（以前 `clean`）。不是 candidate 的照旧 `clean`。
4. 不变的：脏文件的全部路径；干净 ∧ 云端还在（同版 / 有新版）= `clean`；从没同步过的干净文件 = `clean`；离线的非 candidate = `clean`。

测试 `test/resolve.test.ts` 末两条（云端被别处删了 × 三个选项；云端还在 / 有新版 / 离线不弹面）。461 过。
消费方：KudsRocket v0.1.47 收货；gallery 的 `resolve` 动词零改动即受益（它的 pendingGone 徽章说明还写着「可「重新上传」推回云端，或「删除」」= 0.7.2 词汇表之前的旧字，gallery 下次动时改）。

## 0.18.6（2026-10-17，patch，审计修补）：「云端覆盖本地」在云端没了的场合只在云端**此刻**确实没有时才动；撞名不再抛错

> added 20261017 by Claude Fable 5.1（审计 0.18.5 时坐实；user「123都修」）

探针坐实的窟窿（0.18.2 的脏分支和 0.18.5 的干净分支都有）：面开着的几分钟里别的设备把这份传回了云端（或从回收站恢复），人选「云端覆盖本地」→ 两条分支调的都是双向 `delete`，它自己再查一次云端、查到有就把**回来的那一版**也移进云端回收站；干净分支还把本地硬删（它以为云端回收站里有备份）；app 随后说「云端那份已经没了，这台的那份移到回收站了」= 假话。字节能从云端回收站找回，但动了别的设备的新版本、结果报错话。

改法：
1. `delete.ts` `DelOpts.expectCloudAbsent`：开着时云端查到有 → `{ status: "cancelled", reason: "cloud-present" }`，两边都不动；离线 / 问不到云端 → `cancelled / offline`（不盲排云删）。`resolve()` 的 absent / never 两条分支都走它（`delIfCloudAbsentSF`，trashed 之后才摘补推队列），返 `{ status: "unresolved", reason: "cloud-reappeared" }`——人再按一次就是正常的「云端有新版 / 冲突」路（干净的 = clean + pullIfClean；脏的 = changed 面）。
2. 干净副本选「本地覆盖云端」改走和脏分支**同一条** vetted push（断旧谱系、标脏、`pushMod.push(surfaceCollision: true)`）：云端此刻已有同名别的文件 → 不再抛 `CloudNameCollisionError` 报 error，而是再弹一张「云端有新版本」的面，人再选（选云端 → took-cloud、本地进备份箱；选本地 → pushed、云端那份进备份箱）。0.18.5 为此提出来共用的 `reuploadBody` 收回，`reupload()` 恢复原样。

### 行为差异
1. absent / never 场合选「云端覆盖本地」：云端此刻有 → 以前两边进回收站 + 报 trashed；现在两边不动 + `unresolved / cloud-reappeared`。离线 / 问不到云端 → 以前走离线删除（本地进回收站 + 可能排云删）；现在 `unresolved / offline`，不动。
2. 干净 ∧ 云端没了 选「本地覆盖云端」撞名：以前 `ui.reportError(error)` + `not-pushed / error`，文件留脏无基准；现在第二张面（changed）。
3. 其余不变。`DelOpts` 多一个可选字段；`ResolveOutcome` 类型不变（reason 多了 `cloud-reappeared` / `offline` 两个值）。

测试 `test/resolve.test.ts` 末三条（干净 / 脏 两条分支的「面开着时云端回来了」；干净 keepMine 撞名 → 第二张面两种选法）。464 过。
