## 1. 毛病

2026-11-12 下午 user 在办公室一台 Windows 机器上（Edge，小黑屋开发版 v3.0.20）打不开云端：登录正常、列文件正常，下载文件内容连着失败十几次，每次都是 `downloadUrl: network fetch failed (TypeError: Failed to fetch)`。下载走的是微软另一台发文件的服务器。黑匣子里的信息**分不清**是网络拦了那台服务器（通常几十毫秒就失败）还是那边没回音（通常十几秒）。15:59:11 还有一行光秃秃的 `timeout`，看不出是哪个请求。

之后 user 点离线继续，弹出「云端有新版本，保留哪一边」，主按钮是「云端覆盖本地」——那一下要下载，当时根本完不成。

## 2. 改了什么

1. **`CloudNetworkError` 加两个可选字段**（`src/base/errors.ts`）：`stage`（`"graph"` = 经 Graph 接口；`"content"` = 下载文件内容）、`host`（只有主机名）。构造器第三个参数可选，老的两参写法照旧。
2. **下载报错带上主机名、文件名、用时**（`src/base/providers/graph.ts`）：
   - 整份下载 `downloadItemBlob`：`downloadUrl: network fetch failed host=… file="a.txt" after=1234ms (TypeError: Failed to fetch)`，stage = content。文件名来自拿下载地址那一趟 GET 回来的 item（本来就带 `name`，零多余请求）。
   - `downloadUrl failed <状态码>` 那一支也带 `host=… file=… after=…ms`（还是普通 Error，status 语义不动）。
   - 按范围下载（`downloadItemRange` → `rangeFromUrl`）同样带；下载地址缓存连文件名一起记。
   - 经 `graphFetch` 的网络错：stage = graph，带 `host=graph.microsoft.com after=…ms`。
3. **签名地址不出报错（硬规矩）**：所有网络报错的 `String(e)` 过 `scrubUrls`（字里任何 `scheme://…` 换成主机名），cause 过 `safeCause`（原错的字里带地址 → 换一份同名、字被洗过的；不带 → 原样保留同一个对象）。上传会话、复制监控这两处打的也是带签名的地址，一起洗了、补了 `host`（不给 stage）。`graphFetch` 的 `pathOrUrl` 是整条地址时（分页的 nextLink）只留主机名。
4. **收藏夹同步超时说清是谁**（`src/works/folder-flow.ts`）：以前 `new Error("timeout")`，现在 `timeout: collection "<名字>" pull got no answer in 15000ms`（推同理）。15:59:11 那一行就是它：两个仓里只有这一处会抛光秃秃的 `timeout`，小黑屋的收藏夹（`enc-dict`）同步走这里，超时后以 log 级进黑匣子。
5. **冲突面多一个事实 `contentFailing`**（`src/works/content-health.ts` 新文件 + `cloud-sync.ts` + `create-store.ts`）：
   - 只记一件事：这个页面里（= 这个 store 实例）最近一次下载文件内容失败了、之后还没成功过。不猜原因、不设时限、不落盘；成功一次就清掉。
   - 「下载文件内容」= cloud-sync 向 provider 要字节的四处：`pull`（整份）、`pullTail` / `pullRange`（预览按范围）、推完核尾巴（`_confirmOurUpload`）。作品和 collections 两个 cloud-sync 实例共用一份。资源那台引擎（stream）不进来。
   - `ui.resolveConflict` 的三个调用点都多给 `contentFailing: true | false`（一直给，不省略）。
   - **库里任何决定都不看它**：派发、先备份再覆盖的顺序、自愈，一个字没动。

## 3. 行为差异

| 场景 | 2.3.2 | 2.3.3 |
|---|---|---|
| 下载文件内容被网络拦下 | `downloadUrl: network fetch failed (TypeError: …)` | 同一句 + `host=… file="…" after=…ms`；`stage: "content"`、`host` 字段 |
| 发文件的服务器回了非 2xx | `downloadUrl failed 403` | `downloadUrl failed 403 host=… file="…" after=…ms` |
| 拿到 200 之后读体中途断 | 裸 `TypeError` 一路上抛 | `CloudNetworkError`（`downloadUrl: body failed …`，stage content）——和按范围下载的 body failed 早就是这样 |
| Graph 接口网络错 | `Graph GET <路径>: network fetch failed (…)` | 同一句 + `host=graph.microsoft.com after=…ms`；`stage: "graph"` |
| 收藏夹同步 15 秒没回音 | `timeout` | `timeout: collection "<名字>" pull got no answer in 15000ms` |
| 叫冲突面 | ctx 没有 contentFailing | ctx 多一个 `contentFailing`（宿主不读 = 和以前一样） |
| fetch 自己的报错里带着整条地址（别的运行时） | 地址原样进报错 | 换成主机名；cause 也洗 |

重试语义不变：`CloudNetworkError.status` 仍是 undefined，`push.retriable()` 的判定和以前一样（裸 TypeError 也是 undefined）。唯一按错误名字分支的地方是 `dirty.pushAll` 的失败原因（`create-store.ts`）：推送撞冲突后拉云端比字节那一拉如果读体中途断，原因从 `"error"` 变成 `"network"`，更准。

## 3½. 为什么默认开、不走「默认关 + 消费方显式开」（本库规矩 ④）

- 报错的字、两个可选字段、`contentFailing` 都是**信息**，不改变库里任何一个决定（谁赢、要不要备份、要不要重试、要不要弹面）。宿主不读它们 = 和 2.3.2 一样；默认关 = 每个 app 收库时都得记得打开一个「让报错说清楚」的开关，没有意义。
- 签名地址不出报错是**安全**的硬规矩：做成开关等于允许关着泄地址。
- 唯一改了类型的是「读体中途断」：它本来就是网络层失败（`CloudNetworkError` 的契约 = fetch 那一层的失败），按范围下载从 2.0.0 起就这么包；宿主拿到的是更准的分类（小黑屋会显示「网络问题」那句而不是一串英文）。重试语义不变（见上）。

## 5. 施工单没写到、我先这么做了的（请统筹审）

1. **读体中途断也翻成 `CloudNetworkError`**（第 3 节表里第三行）。施工单只说「报错带上…」；那条路以前是裸 TypeError，带不上主机名和用时，所以一起包了。
2. **`contentFailing` 管的范围**：cloud-sync 的四处（含预览按范围、推完核尾巴），作品和 collections 共用；stream 引擎不算。任何失败都算（网络错、非 2xx、拿下载地址那一趟失败），因为施工单说「不猜原因」。
3. **`/content` 兜底那一支**（Graph 没给 downloadUrl 时走 `GET /me/drive/items/<id>/content`，微软再跳到发文件的服务器）经 `graphFetch`，所以 stage 是 `"graph"`，虽然它其实在下载内容。实际很少走到（Graph 对文件都会给 downloadUrl）。按施工单字面做了，没另加分支。
4. **Graph 接口网络错也带了 `host=… after=…ms`**（施工单只要求 stage）；分页地址只留主机名。
5. **上传会话 / 复制监控**：洗了地址、补了 `host` 字段，不给 stage（不属于 graph / content 两类）。
6. **一处要注意的局限**：下载**一直不回**（不是被拦、是挂着）时，`contentFailing` 要等那一趟真失败才会变真。小黑屋现在没开请求超时 = 永远不会；第 4 条开了以后整份下载的超时是 15 分钟（`DEFAULT_GRAPH_TIMEOUTS.blob`），也就是这种情形下面上要 15 分钟后才说实话。收藏夹同步的 15 秒超时**没有**记进来，因为那 15 秒里可能卡的是列文件那一步，不确定是下载。要不要缩短小黑屋的 blob 超时、或者把超时也算进来，是设计决定，我没动。出事那天是几十毫秒就失败的那种，这次的改动能覆盖。
7. 库仓 `CLAUDE.md` 的「行为变更」清单（⑪ 是 2.3.2）这一版要不要加一条 ⑫：那是规矩文件，我没写，由统筹定。
