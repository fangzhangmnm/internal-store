## 1. 毛病

库里几处会宣布「这份文件已经和网盘一致」：清掉待传、把网盘的版本号记成基准。宣布之后本机那份就允许被别的设备的新版直接换掉、允许被腾空间清掉。以前判断「一致」靠「这个文件被保存过几次」：动手前记一个数，动手后再看，没变 = 没人动过。可这个数在保存**发出**时就加一，字节要过一会儿才落盘——中间这一下进来的推送拿着上一份字节、看见数没变，就宣布了一致，随后那次保存才落盘：本机比网盘新、待传却是 0。之后别的设备一改，这台干净快进，把没传上去的那份**无备份地**换掉。

最常见的叠法：自动保存（只落本机）和自动续推（回前台 / 回线 / 登录后的 `dirty.pushAll`）撞在同一刻。各家都够得着，app 不用做错任何事。

服务目标（家族根 `ai-docs/20261016-data-safety-model.md` §2）：第 1 条（网盘赢家不被静默覆盖）、第 2 条（没推的本地改动不丢）、第 3 条（诚实：没传完不许说传完了）。威胁行 §3：A 组「保存和推 / 拉撞车」那一类（0.15.2 修过「动手之后又保存」那一半，这次是「动手之前已经发出、还没落盘」那一半）。

## 2. 改了什么

1. **发出即占位**（`create-store.ts save()`）：标脏、取号、进同名串行段三步在同一个同步步骤里，中间没有 await；转数组和封装挪进队里。
   - 落盘顺序 = 发出顺序（以前封装快的先落：两次叠着的保存，盘上最后可能是先发出的那份）。
   - 队里任何别的动作（推送、采纳网盘字节、加密转换、改名、删除）轮到自己时，它之前发出的保存都已落盘；它之后发出的一定排在它后面。
   - 封装按**轮到时**盘上的加密状态做（以前「加密这篇」和一次保存叠着时，保存按「还没加密」封好、在加密之后才落盘 = 标着加密的稿子盘上是明文）。
2. **盘上账本** `src/works/disk-ledger.ts`（纯内存、每个标签页一份、零 IO）：每次保存发出拿一个号；落盘记「盘上 = 几号」；库自己写盘（采纳网盘字节、加密转换、改名写新名字、首次取回、下载会话落地）记一个新号。唯一判据 `settled(name, g)` = 没有在路上的保存 ∧ 盘上就是 g。**每一处宣布一致之前对号，对不上就不宣布**（待传留着；该接上的基准照接）。
3. **逐处对号**（设计稿 2.3 的表，全部接了）：

| 在哪 | 号从哪来 | 对不上时 |
|---|---|---|
| `push.ts doPush` 推成了 | `opts.gen`（`save()` 自己的号）；没给 = 开头读 `ledger.disk`（调用方在同名串行段里读盘） | `onPushed(…, true)`：基准挪到新版本号，待传留着 |
| `doPush` 撞 412 自愈（`tryHeal`） | 这次推的号 | 认领网盘那一版当基准、仍待传（以前是先宣布、再看保存次数补标脏，中间隔一个 await） |
| `doPush` 冲突面选了「本地覆盖云端」（`weakOverride`） | 这次推的号 | 同上（以前**没有**任何补救，直接宣布） |
| `safe-resolve safePull`（云端覆盖本地 / 干净快进） | 覆盖后 `ledger.wrote`；另记备份那一刻的 `d0` | 备份之后盘上换过 = 按「途中保存过」处理（快进作罢 / 人选了云端 → 再备份一次）；覆盖后对不上 = 不提交谱系 |
| `create-store adoptLocal`（下载会话落地） | `ledger.wrote` | 不宣布 |
| `create-store encSwap`（加密 / 解密 / 换密码） | `ledger.wrote` | 推成了也仍待传 |
| `identity rename` 推新名 | 写新名字后 `ledger.wrote(新名)` | 同 doPush |
| `identity acquire`（首次取回） | `ledger.wrote` | 不宣布 |
| `head.forget`（删除 / 腾空间 / 断谱系，十几处） | — | 包了一层：同一步 `ledger.forget` |

4. **设计稿表外、这次一起归了类的三处**（读本机字节来推 / 比，以前都在队外读）：
   - `file.resolve()` 的「本地覆盖云端」两条（脏分支、云端刚没了的干净分支）：读盘挪进 `encode`（在队里读）。
   - `file.resolve()` 弹面之前比字节（2.2.3 那条自愈）：字节和它的号在队里一起取，拉网盘那一下**不占队**（慢网时保存不被卡住），认领之前对号。
   - `file.reupload()`：读盘 + 推包进同名串行段。

## 3. 行为差异

**没有叠着的保存时，一个字节都不变**：现有 582 条测试一条没改、全过（2.3.1 的两条待办换成了正式测试）。叠着的时候：

| 场景 | 2.3.1 | 2.3.2 |
|---|---|---|
| 自动保存撞上自动续推（同一刻 / 隔一个微任务） | 网盘旧、本机新、待传 = 0 | 续推排在保存后面，推的就是新的那份；两边一样、待传 = 0 |
| 「存并推」紧跟一次只落本机的保存 | 同上（错） | 推的是前一份，推完待传 = 1；下一次推把后一份推上去，谱系不断、不弹面 |
| 前一次写盘卡 0.3 秒，期间来了后一次保存，之后别的设备改了网盘 | 干净快进把后一份吃掉、不留底 | 待传 = 1 → 不快进 |
| 两次保存叠着、先发出的封装慢 | 盘上最后是先发出的（旧的） | 盘上最后是后发出的 |
| 保存发出了还没落盘时，冲突面选了「云端覆盖本地」 | 那次保存不在备份里、落盘后被覆盖 | 它先落盘、进备份，再被网盘那版覆盖 |
| 保存发出了还没落盘时「加密这篇」 | 盘上明文、待传 = 0 | 盘上是容器、待传 = 1 |
| 推送撞冲突、人选了「本地覆盖云端」，问的时候又保存了一次 | 待传 = 0（错） | 待传 = 1 |
| 上传回执丢了，之后保存一次、紧接着自动续推 | 续推拿旧字节去比、比上了就认领 → 待传 = 0 | 续推推的是新的那份，比不上 → 留待传（不盲盖网盘） |
| 保存写盘失败 / 锁着封不上 | — | 不算在路上，之后的推送照常宣布一致（不会永远卡在待传） |

宿主能感觉到的：

- **保存的 promise 现在要等前面排着的动作做完**（推送、加密转换、改名……）才落盘、才 resolve。以前封装那一步在队外先跑，只有写盘在队里等。上传在飞时保存本来就要等它（写盘一直在队里），挪进去的只是转数组和封装那一小段，不新增等待对象。
- 叠着保存的那一种里，**会多推一次**（「存并推」推的是它自己那份，后一份等下一次推）。没有新增弹面。
- 回执丢了之后又改过：以前偶尔会「碰巧认领」、待传归零（其实认领的是旧的那份）；现在推新的、比不上 → 待传留着，之后推送撞冲突面问人。这是**把一个假的「已同步」换成一张真问人的面**。

## 3½. 为什么默认开、不走「默认关 + 消费方显式开」（本库规矩 ④）

- 这不是新行为，是「宣布一致」这条既有契约的补全：`local-head.markSynced` 的注释写的就是「盘上字节 == 云端某版」，0.15.2 修的是同一个洞的另一半。默认关 = 洞继续开着，它**真丢字节**（第 1 节），而且 app 不做错任何事就够得着。
- 没有叠着时 `settled` 恒为真，判断不改变任何现有路径：582 条原样绿就是证据。改变的只有「以前说了假话」的那些时刻，方向全是**更保守**（待传留着、多推一次、问人）。
- 改错的方向有两种：该留的清了（就是现在的毛病）、该清的留了（待传永远不归零）。第二种由 I9（写盘失败 / 锁着封不上之后照常归零）和那 582 条钉着。

## 5. 和设计稿不一样的地方

1. **只改排队那一步时，I5 没有变绿**（设计稿推断它会）。原因：「云端覆盖本地」的第一次备份在队外、动手的最开头做，那时还没落盘的保存赶不上这份备份；排队只保证它在覆盖之前落盘，不保证它进备份。补上它的是 2.3 表里 `safePull` 那一行（备份那一刻记 `d0`，覆盖前盘上换过 = 再备份一次）——这一行本来就在设计里，只是推断时把功劳记到了 2.1 上。I6 在只改排队时「盘上是明文」已经好了，「待传被加密清掉」要等 `encSwap` 对号。
2. **账本没有 `move(from, to)`**：改名写新名字那一下按 R3 调 `wrote(新名)`，旧名随 `head.forget` 一起清，两件就够；`move` 没有调用者，不留。
3. **`forget` 不清「在路上」**：删除 / 腾空间时还有保存在路上，它落盘时照样记账（宁可多留一次待传，不让判据在它落盘前就说「对得上」）。
4. **I4 / I6 的「按住封装」没有改 `src/testing/mock-encryption.ts`**（设计稿说在那上面加延迟钩子）：测试里把替身返回的对象包一层就够了，`./testing` 门牌的接口因此一个字没变。
5. **设计稿表外多归了三处**（第 2 节第 4 条）：`resolve()` 的两条本地覆盖云端、`resolve()` 弹面前比字节、`reupload()`。`resolve()` 比字节那一处特意没有整段放进队里：拉网盘那一下可能被「跳过到离线」打断，整段占队会让之后的保存一直等着。

## 6. 只读看过、没改的

- **`works/collection.ts`（设置、阅读位置这类小集合）没有同一类毛病**：它推上网盘的是内存里的那份（`env`），推完要比「并回之后的内存 == 推上去的」才清待传（K12），不靠保存计数；本机缓存晚一步写（`localTimer`）只影响本机缓存，不影响网盘那份。
- **多个标签页同开一份文件**：账本每页一份，别的页的保存这一页看不见——和 2.3.1 一样，不变好也不变坏（设计稿第五节）。
- `head.editCount` 和 `safePull` 里靠它的三道判断都留着（偏保守，和新的一层不冲突）。
