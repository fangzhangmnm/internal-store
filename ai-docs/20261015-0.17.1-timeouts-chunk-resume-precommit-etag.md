# 0.17.1：请求超时、分块上传接着传、提交前核 eTag、push 退避拉长

> created 20261015 by Claude Fable 5.1 · as-of 0.17.1 · user 2026-10-15「库开始修」（KudsRocket 会话；起因全在 `20261014 KudsRocket/ai-docs/20261015-fable-snapshot-sync-analysis.md`）。patch：不改公开 API、不加持久化。

## 改了什么（全在 `src/base/providers/graph.ts` + `src/works/push.ts`）

1. **每个 Graph 请求带超时**（`AbortSignal.timeout`）：元数据 / 列举 / 会话 30 s；一块 5 MiB 的 PUT 120 s；一片 byte-range 60 s；整文件下载 15 min。到点中止 → `CloudNetworkError`（和断网同一类：可重试、留 dirty）。老浏览器没有 `AbortSignal.timeout` → 不带 signal，行为同 0.17.0。
   起因：iOS 锁屏 / 切后台后在途的 fetch 常常**永远挂着**（既不成功也不报错）→ 消费方的「正在存」锁、在途计数全挂死（KudsRocket 10-15「多锁几次，全卡死了，手动存档都不行了」）。
2. **分块上传单块失败接着传**：网络错 / 429 / 416 / 5xx → `GET uploadUrl` 问 `nextExpectedRanges`，退避 1 / 2 / 4 / 8 / 16 s，从那里继续；连续 5 次失败或会话没了（404）→ `CloudNetworkError`，上层（push.ts）整份重试。以前一块失败 = push 整份从头再来（iPad 10-14：6.8 MB 快照第二块 `Load failed`）。
   跨刷新 / 跨页面续传要存会话 URL = 新持久化结构，**没做，另问**。
3. **提交最后一块前核一次 eTag**：`If-Match` 只在 `createUploadSession` 时核，最后一块落地无条件 → 两台设备同时覆盖同一文件有「上传那几十秒」的窗口（分析报告 §4）。现在有 base eTag 的上传在传最后一块前 `getItemByPath` 比一次，变了就 `DELETE uploadUrl`、抛 412（cloud-sync 翻成 `CloudConflictError` → 冲突面）。窗口缩到最后一块那几秒。代价 = 每次分块覆盖多一个 GET。
4. **push 退避**：4 次 × 200·n ms（共 2 s）→ 5 次、1 / 2 / 4 / 8 s（共 15 s），熬得过 iOS 切网络那几秒。

## 测试

`test/graph-upload-resilience.test.ts`（假 fetch）：一块网络错 → 4 次 PUT 不是 6 次、问了一次会话、退避 1 s；提交前 eTag 变了 → 412 + 会话撤掉 + 最后一块没传；连续失败超上限 → `CloudNetworkError`；挂死的 fetch 到点 → `CloudNetworkError`。

## 没做 / 要 user 定

- 跨刷新续传（存会话 URL）——新持久化，另问。
- `pushAll` 会不会排在一个挂死的推送后面：有了超时之后挂死最多 120 s，先不动。
- 消费方收货：KudsRocket 先收（它报的案）；WeebPaint / WXHW / CatsUp / JRB 各自钉的版本更老，收货时按 pwa-cloud-store §3 看编译错误清单。
