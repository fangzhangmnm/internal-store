# 密码来源 = 生成的口令短语 + 平台凭据管理器（不是人脑，也不是纸）
> created 20260909

**Status:** accepted（方向，2026-09-09 user 拍板）· **未实现**（user：「今天不用急着做」）
— 延续 ADR-0012 的密码政策行（`do not pre-stretch` / `do not enforce`），**不推翻它**。

## Context

起点是一次算法侧的合规审计（「我们的加密符合 quantum readiness 吗」）。审计结论是**算法侧无事**：
容器是 AES-256（7z payload）+ PBKDF2-SHA256×250k→AES-256-GCM（peek），**零公钥密码**。Shor 只破公钥，
Grover 对 AES-256 只把 2²⁵⁶ 降到 2¹²⁸——全世界正在迁移的那部分东西我们从来没有过，无可迁。

于是真正的弱点浮出来，而它不是数学问题，是**口令的来源**问题。约束集：

1. **anti-abandonware**（ADR-0006）：app 死了，7-Zip + 密码必须还能捞出原文。这是硬产品价值。
2. **零基础设施**：我们没有服务器，无密钥托管。
3. **用户会丢一切**——设备、纸、记忆。user 原话：「anti abandonware就是用户永远会丢东西丢设备」。
4. **10 年可取回**。
5. **非技术用户**（艺术家）。

第 2、3、4 条叠在一起是最狠的：没有服务器 + 用户会丢光 + 十年后还要能开。**必须有东西活下来**，
问题只是「用户手上最耐久的东西是什么」。

ADR-0012 在这件事上已经钉过两颗钉子，本 ADR 全部保留：
- **`Do not pre-stretch the password`** —— 必须在 7-Zip 里原样可打。
- **`do not enforce a strong passphrase`** —— 不强制强度，「surface brute-force risk once, non-blocking」。

外部佐证（非用户语料，公开来源）：**NIST SP 800-63B 在 2017 年删除了密码复杂度规则与强制轮换**，
理由是复杂度要求会诱导可预测的派生变体，净效果**降低**安全性。0012 那句「不强制」与 NIST 同向，
本 ADR 要解决的是它留下的缺口：**不强制之后，怎么让用户不费力地拿到一个好口令。**

## Decision

1. **生成，而非要求。** 密码框旁给一个骰子按钮，吐 6 词口令短语（7776 词表 ≈ 77 bit）。
   user：「A好主意」。**提供，不强制**——一强制就退回 0012/NIST 明确否决的那条路。
2. **生成的短语本身就是字面 7z 密码**，不经任何包装层。anti-abandonware 因此**完整保住**：
   7-Zip 输这个短语直接开，和今天一模一样。
3. **默认托管在平台内置凭据管理器**（Safari / Chrome / iCloud 钥匙串 / Google 密码管理器）。
   user：「其实我反而觉得还是抱password manager大腿吧」。用户**从不需要背，也从不需要纸**。
4. **纸 = opt-in 冗余，绝不强制。** 提供「显示我的口令」+ 复制/打印，想抄进 1Password、想打印的
   自己按。默认不存在纸条。
5. **密钥绝不进 OneDrive**，不与密文同处。见下「原则一」。

## 两条原则（为什么托管给浏览器是免费的，而托管给微软不是）

**原则一：把密钥交给"已经能看见明文"的一方是免费的；交给看不见明文的一方是新增信任。**

浏览器现在就能看到画布上的每一个像素。Safari 若恶意，加密早已无意义。所以把口令交给
Safari/Chrome 的凭据管理器**没有新增任何信任**——是同一个已经在信的东西。
反过来，密钥进 OneDrive 就是新增信任，因为微软本来看不见明文。**所以：密钥可进浏览器，绝不进 OneDrive。**

**原则二：provider split。** 密文在微软，密钥在苹果/谷歌，**任何一方单独都读不出画**。
这是零基础设施白拿的真实安全属性，不是将就。与 ADR-0022（隐私墙外包给微软的 scope enforcement）
同源思路：把墙包给有红队的人，只是这次刻意包给**两个互不相同**的人。

## 秘密只可能来自三个地方（完备枚举）

零基础设施 ⇒ 不能是我们。剩下：

| 来源 | 载体 | 状态 |
|---|---|---|
| 人脑 | 生成的短语（可记，但不必记） | 本 ADR |
| 设备/平台 | 凭据管理器；将来可加 WebAuthn PRF passkey | 本 ADR（passkey 需密钥分层，未做） |
| 物理 | 纸 | opt-in |

三条**互为冗余**。关键判据：**一个恢复秘密只有在它是唯一入口时才是单点故障**；入口越多，
失效条件从「丢了它」变成「同时丢光全部」。user 否决强制发纸正是因为它当时是被设计成唯一入口的。

## 被否决的替代方案（勿再 re-litigate）

- **强制打印恢复卡。** user 2026-09-09 明确否决：「B无法接受」「多一张纸就是一个会丢的单点故障」。
  纸只能是 opt-in 冗余。
- **密钥分层的原版形态**（内容密钥随机、口令只包住它、另发高熵恢复码）。两个理由：
  ① 它依赖一张必发的纸，撞上上一条；
  ② **我当时把它的 rekey 收益说大了**——「换密码只重包、内容不动」防不住**已经拿到密文+旧密钥**的
  攻击者，重包一万次他手上那份照样能解。真泄露就必须换内容密钥，也就必须重加密。
  rekey-without-re-encrypt 只在「口令被肩窥、但文件未泄」这个窄场景有用。
  → 密钥分层**不是废案**，但它的正确卖点是「让 passkey / 多入口能挂上来」，不是「修 rekey」。
    要做仍属红线区，须 escalate。
- **把密钥存进 OneDrive**（与密文同处）：违反原则一，等于加密白做。
- **Shamir 社交恢复**（切片存给朋友）：非技术艺术家用户，否。
- **强制强密码规则**：0012 + NIST SP 800-63B 双重否决，见 Context。

## 这不违反既有红线（澄清，防未来 agent 误判）

- ADR-0012「**Password is memory-only, never persisted**」**仍然成立**。我们依旧不往 IDB /
  localStorage / 云端写任何口令。凭据管理器是**平台的**存储、经用户点「保存密码？」授权进入，
  不在我们的存储面内。
- ADR-0012「do not pre-stretch」「do not enforce」**仍然成立**：短语是字面 7z 密码（可打），
  且骰子按钮是**提供**不是**强制**。
- 硬规则 #6（appfolder scope）不受影响：本 ADR 不改任何 scope。

## 落地清单（app 层，全部**未做**）

1. 密码 sheet 改成**真的 `<form>` + `<input type="password">`**，`autocomplete="new-password"`（新建）
   / `current-password`（解锁），稳定 `name`/`id`，真 submit。
   **现状 `promptPassword` 是自绘 sheet，浏览器认不出来，所以从来没弹过「要保存密码吗」——
   这一条就是全部魔法所在。**
2. **不禁用粘贴**。
3. 骰子按钮：生成 6 词短语并默认填入（提供，不强制）。
4. 「显示口令」+ 复制/打印，opt-in。

## 残余风险（诚实）

- 凭据按 **origin** 绑定。app 换域名 = 所有已存口令成孤儿。这是本方案新增的一个耦合。
- 用户同时丢光平台账号与记忆 = 数据没了。这是 E2E 加密的底价（Signal / iCloud 高级保护同价），
  无法在零基础设施前提下绕开。
