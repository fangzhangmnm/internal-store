# 宿主收同步库 2.3.6 的注意事项（从 2.2.x 上来）

> created 2026-11-12 by Claude Fable 5.2（小黑屋维修线统筹）
> as-of 同步库 2.3.6（提交 773ffe9）/ 2026-11-12
> 给谁看：还钉在 2.3.2 之前的宿主——三维（2.2.7）、KudsRocket（2.2.4）、读书（2.2.4）。画画、写歌（2.3.2）收 2.3.6 只需要看第三、四节。
> 起因：user 11-12 问「会不会建模软件的同步库太旧导致有 bug」，一查确实有；随后同意三维收新库（「可以可以收同步库，然后在你建议的排期可以」，Catsup统筹转述）。
> 每一条后面写了是**跑过**的还是**读代码**得出的。没写的按读代码算。

## 一、为什么要收

2.3.2 之前的版本里有一个丢数据的毛病（周账 F-188 / F-238；修法 = `20261110-2.3.2-disk-ledger.md`）：

- 自动保存正好撞上上传的那一下，后存的那一份没传上去，却被记成「已同步」。本机比网盘新，待传计数是 0。
- 之后别的设备改了网盘、这台回来核对：这台以为自己是干净的，直接把本机那份换成云端的，不留底。后存的那一版就没了。
- **跑过**：把 11-10 的复现脚本（提交 dd5b2ba 里的 `test/repro/f188-dirty-cleared-before-bytes-land.repro.ts`）原样拿到 v2.2.7 的导出副本上跑，五种时序里四种复现，脚本演的后果是「备份箱 0 份」。同一脚本在 v2.3.5 上五种全过。
- **没查**：各宿主自己的保存和上传节奏会不会踩到这四种时序。宿主如果自己把保存和上传排成了一条队，可能踩不到。收之前在宿主里对着这四种时序读一遍会话层，能写一个会红的探针最好。

在收之前，宿主可以告诉 user 的话：换设备前，在这台上最后改完多等一下，看到已同步再走。到另一台发现最后那一段不在，别在那台上改这份文件；回原来那台，做一点小改动再存一次。

## 二、宿主这一头要改什么

**必须改的：没有。**（**跑过**对照：比了 v2.2.7 和 v2.3.5 的接口清单 `api/store.d.ts`、`api/store.api.md`；2.3.6 只多 `GraphTimeouts.upload?`。）

- 接口只有新增的可选项，没有删掉的、没有改名的、没有新的必填声明。
- 两个新开关 `lockByDefault`（修改锁）和 `fileMarks`（星和收起）默认关，不传 = 2.2.7 的行为。收库这一轮别开：`fileMarks` 一开就会在网盘上建 `.<appId>/store.file-marks.json`；`lockByDefault` 是家规里要专门迁移一轮的事。
- 本机数据库没有迁移（`src/works/migration.ts` 这几版没动）。所以收了之后要退回旧版，本机数据按理是兼容的。这一条是看改动的文件清单得出的，没有真的来回装过。
- 从 2.2.4 上来的（KudsRocket、读书）另外要读三份：`20261104-2.2.5-resolve-heal-escape.md`、`20261104-2.2.6-save-offline-and-item-cloud-sealed.md`、`20261105-2.2.7-dispose-closes-collections-and-inflight-frames.md`。那三版我这次没有重新审。

**不用改代码、但行为变了，宿主的测试要对一遍的：**

1. （2.3.2）保存的 promise 要等同一份文件前面排着的动作（上传、加密转换、改名）做完才落盘、才返回。以前封装那一小步在队外先跑。上传在飞时保存本来就要等，所以新增的等待很少；但宿主里凡是假设「只存本机的那一下很快回来」的地方看一眼。
2. （2.3.2）待传计数在保存叠着的时候会比以前多留一会儿：以前错报 0 的地方现在是 1；叠着保存会多推一次；回执丢了之后又改过的，以前偶尔「碰巧认领」成已同步，现在留着待传、之后撞冲突面问人。测试里断言「此刻待传是 0」的地方可能要跟着改。这正是要的那个修。
3. （2.3.3 / 2.3.5）网络报错的字变了。例：`downloadUrl: network fetch failed host=… file="…" after=…ms (failed-to-fetch)`。不再带浏览器给的原话；报错对象多了 `stage`（`"graph"` 或 `"content"`）和 `host`；`cause` 换成只有名字和类别的替身。按 `name === "CloudNetworkError"` 判的不受影响。测试里写死了报错原文的断言要改。
4. （2.3.3）同步收藏夹超时的那句从光秃秃的 `timeout` 变成 `timeout: collection "名字" pull got no answer in 15000ms`。
5. （2.3.3）`ui.resolveConflict` 的参数多一个可选的 `contentFailing`：这个页面里最近一次下载文件内容失败、之后没成功过。不理它就和以前一样。
6. （2.3.5）Graph 回非 2xx 时带的错误正文截到 300 个字符。

三维的代码我搜过一遍（**读代码**）：读登录续签那几行日志的 `noteRenewFailureLine` 不受影响（库里登录那部分这几版没动）；三维里读 `.cause` 的都是它自己的 `OpApplyError`。

## 三、请求时限（开着 `transport.timeouts` 的宿主必读）

- 2.3.3 及以前：4 MB 以内一次传完的上传，用 `meta` 那档（默认 30 秒）。
- 2.3.4、2.3.5：改成了 `chunk` 那档（默认 120 秒），而且是默认就生效。**这是错的**，违反本库规矩 ①（传输层行为变更做成显式开关、默认 = 变更前）。是统筹裁定时没读规矩。收过这两版的只有小黑屋，它没开请求时限，所以没有宿主实际受影响。**开着请求时限的宿主不要停在 2.3.4 / 2.3.5。**
- 2.3.6：单列一个可选项 `upload`。不写 = `meta` 那档（和 2.3.3 及以前一样）；写了用写的值。分块上传的每一块照旧 `chunk`。
- **跑过**（统筹自己写的脚本，三个版本各一遍）：开着时限、不写 `upload` 时，一次传完的上传在 2.2.7 和 2.3.6 上都按 `meta` 那档掐断，在 2.3.5 上按 `chunk` 那档；2.3.6 上写了 `upload` 按写的值；没开时限时没有时限。

这个数为什么归宿主定：两头是顶着的。

- 要宽：慢网上一个 1–4 MB 的文件 30 秒传不完，会被掐断、重试、再掐断，一直传不上去（要每秒 33–140 KB 以上才过得了 30 秒）。
- 要窄：上传卡死时，宿主要靠时限到点才知道。三维的说明里写着，上传卡死 = 保存一直在进行 = 自动保存全被跳过 = 改动只在内存里。时限越长，这段时间越长。

**这一节的框架要改着读（同日夜）**：上面「要窄」那一条把宿主靠请求时限保命写成了取舍的一头。user 当晚的批评（Catsup统筹转述原话）：「你依靠这么一个本来不是用你做这个东西来保证你应用逻辑的正确，然后反而让别人去牺牲他们的安全要求去来迎合你，这是一个非常严重的纪律问题」「为什么你必须要依靠这个逻辑来保证你不卡死？我觉得这你可能本来就不应该有超时」。三维随即撤回了对时限的任何要求：不写 `upload`，会话层改成「正在存」只管本机落盘。2.3.6 的默认值不因此再动：它等于今天之前一直的行为，依据是本库规矩 ①，不是为了照顾哪个宿主。根子是第六节第 1 条。

另一处照旧默认生效的（理由在 `20261112-2.3.6-upload-timeout-tier.md` §3½）：拿不到下载地址时走 `/content` 的兜底下载，整份的用 `blob` 那档、按范围的用 `range` 那档。以前同一种下载因为走了哪条地址而有两个时限，是分档时漏了。

## 四、能不能只换同步库

能。

- 图库库 0.8.10 的包里要求同步库 ≥ 2.1.2、界面零件库 ≥ 0.1.2。加密库 0.2.2、参考窗库 0.5.0 的包里对同步库没有要求。同步库自己对别的库没有要求。（**读**的是各个包里的 package.json。）
- **跑过**这个组合的：小黑屋 v3.0.21 = 同步库 2.3.5 + 图库库 0.8.10 + 加密库 0.2.2 + 参考窗库 0.5.0 + 界面零件库 0.1.3，整套端到端 91 个场景。2.3.6 相对 2.3.5 只动了时限那一处。
- 收法：在宿主仓根跑 `bash "../20260813 internal-store/scripts/pull-package.sh" 2.3.6`。

## 六、收了 2.3.6 也还在的已知问题

1. **同一份文件的写队在等人、等网络时被占着**（周账 F-268）。冲突面亮着、或者上传在飞的时候，这份文件后面的保存（包括只存本机的）都排在后面。冲突面一直没人回答 = 之后的保存永远落不了盘。**跑过**：`test/repro/20261112-write-lane-held-while-waiting.probe.ts`（退出码 1 = 还能复现）。宿主能做的：保证问人的面一定有人答得到（小黑屋 `src/gate-faces.ts`）；宿主自己的「正在存」不要一直挂到推云结束。**更正（同日夜，Catsup统筹读三维 `session.ts` 后指出）**：三维图库里的文件，它的崩溃影子就是库的本机副本，不是独立的一层；独立的那个影子库只管没有家的和单个文件的模型。所以上传在飞时，图库里的文件确实没有别的地方落盘。库这一头要出设计，等 user 定。
2. **没人参与的那些判断有三处只剩一层**，还有一层检查（两个标签页互相盖）从加上那天起就没接上：`../ai-docs/20261110-audit-store-swiss-cheese.md`（家族根），里面五条建议等 user 定。
3. **下载回来的字节不和主接口给的文件大小对账**（周账 F-271）。验内容靠宿主的 `validateAdopt`。宿主的文件有魔数或是加密容器就拦得住；纯文本类的要想一想。
4. **报错分不清「根本连不上」和「连上了但浏览器不让读」**（周账 F-271）。`stage`、`host`、`after` 能缩小范围，定不了性。
5. 建文件夹撞名报红条（F-248）；两个写手同时建同一份收藏夹文件、自己撞自己报同名冲突（F-264，三维查出来的）；搬家后口令验证器没进文件夹（F-265，三维）。
6. 2.3.5 起，库自己造的网络报错里没有上游原文。但宿主的黑匣子是给人导出去的，宿主那一层该不该再过滤一遍，各家自己定（小黑屋做了：`src/egress-redact.ts`）。

## 七、测试怎么照着做

**库里现成的：**

- 假云盘 `@internal/store/testing` 的 `createMockProvider()`：`injectFault({ op, kind, status, times })`，`op` 认 `upload` / `delete` / `move` / `copy` / `rename`，`kind` 是 `"error"`（写之前抛）或 `"lostResponse"`（写完了再抛）。
- **它没有「下载不通」的开关。** 现在的做法是把 `provider.download` / `provider.downloadRange` 包一层（样子见 `test/content-failing.test.ts` 开头的 `rig`）。「元数据通、内容不通」「挂着不回」「很慢」这些都还没有正式开关，记在周账 F-271。
- `test/edit-race.test.ts`：保存和上传叠着的各种时序（I3 那一组就是第一节的毛病）。
- `test/graph-download-diagnostics.test.ts`：14 种带假签名的地址写法 × 六条路，查报错里有没有漏。宿主不用重跑。
- `test/graph-timeout-tiers.test.ts`：各种请求用的是哪一档时限。

**小黑屋端到端里可以照抄的做法**（小黑屋仓 `test/e2e-sync/`，真 app + 真同步库 + 真 IndexedDB，只有云是假的）：

- `bridge.ts` 里三个开关：`window.__e2eContentBlocked`（只拦下载内容，列文件和上传照常）、`window.__e2eUploadFail`（上传一律断）、`window.__e2eUploadAttempts`（数上传试了几次）。
- `run.mjs` 里的场景，按名字找：「下载内容不通 · 推送冲突」「冲突面亮着时又来一张问人的面」「回来 · 」开头的那一组（没人改过的稿不许变成待传；改之前是红的）。
- 记 IndexedDB 每一笔写入的探针（场景「先封再存」用的那个）：用来断言「这一步一个字节都没写」。

**放行一层防护之前**：审的人自己写一个攻击脚本去撞，不用被审方的测试。2.3.3 的第一版地址过滤就是看着测试是绿的放行的，后来 14 种写法漏了 9 种。
