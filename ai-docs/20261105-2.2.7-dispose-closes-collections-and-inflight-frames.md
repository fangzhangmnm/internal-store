# 2.2.7（patch）：`dispose` 收掉 collection 的定时器并落盘 + 在飞的目录帧自退

> created 20261105 · 代码 Claude Fable 5.1（WIP commit dab6885）+ Claude Opus 5.5（改两处、测试、发版）· as-of 2.2.7 · user 2026-11-05「1 修」· 家族周账 F-199 · 施工单 = 家族根 `ai-docs/20261105-work-order-dispose-false-alarm-toasts.md` §1

## 1. 改了什么（两处）

1. **`dispose` 先关每份 collection**（`works/collection.ts` 经 `cfg.lifecycle` 交出 `close({flush})`，只给 store 用；`create-store.ts`）：
   - `dispose()`（drain）：排着的本地写**先落盘再关**，在飞的那笔也等完；真落不下去照常 `warning`。
   - `dispose({ drain: false })`（快速拆除）：只取消、**一步也不等**（卡住的 IDB 不许把拆除也卡住）；扔掉的那笔和撞墙的在飞写只进 `log` 级（黑匣子）。
   - 排着的云推两种都只取消：脏账在 kv、字节在本地，下次开库 `init → reconcile` 补推。
   - `init()` 走到一半库被释放：不种初始值、不标脏、不打网（否则 hydrate 撞上关掉的 IDB 会被当成「新库」）。
2. **在飞的目录帧见 `_disposed` 自退**（`create-store.ts` 的 `pushLocalFrame` / `pushRemoteFrame` / `watchFolder`）：每个 await 之后看一眼——不投帧、不 reconcile、不写目录索引缓存、不叫 app 的 `onError`；撞墙的错只进 `log` 级。释放**之前**的失败照常 `error` + `onError`。

## 2. 为什么

- 起因（CatsUp v0.18.38 三张小单查出）：开机半秒内 app 拆空库（没选家的设备）→ ① 400 ms 后本地写撞上关掉的 IDB，用户看到一条英文警告，每次都中；② 正开着图库时目录帧读到一半撞墙 → 红色英文 + 列表画成「读取失败」（CatsUp 6 页并行 18 次中 2 次）。别的 app 搬家 / 登出拆库同样会中。
- **比假警告更严重的一层（Opus 写测试时发现）**：① 那笔本地写是真的没落盘。2.2.6 上 `setItem` 之后 400 ms 内 `dispose` 再马上重开，这次改动**读不回来**（测试 `云推被取消不丢改动` 在 2.2.6 上红在这里）。旧代码靠的是云推定时器晚些还会在拆掉的库上跑一次；离线时就真丢了。
- 服务目标（`ai-docs/20261016-data-safety-model.md` §2）：第 2 条（没推的本地改动不丢）+ 第 3 条诚实（不给用户冒假警告）。威胁行：§3 A5 一类（页面重开 / 开机拆空库）、A12（还原出厂 / 搬家拆库）。

## 3. 行为差异

| 场景 | 2.2.6 | 2.2.7 |
|---|---|---|
| `setItem` 后 400 ms 内 `dispose()` | 本地写撞墙 → `warning`，**这笔没落盘** | 先落盘再关，没有上报 |
| 同上，`dispose({drain:false})` | 同上 | 扔掉那笔，`log` 一行（没有 warning） |
| `dispose` 时排着 1.5 s 的云推 | 定时器照跑，在拆掉的库上推一次 | 取消；脏账 + 本地字节 → 下次开库补推 |
| `dispose` 后迟到的目录帧 | `error` + `onError`，可能投帧、写目录索引缓存 | 只 `log`，不投帧、不写缓存、不叫 `onError` |
| `dispose` 撞上 `init` 进行中 | 可能种初始值、标脏、打网 | 到此为止，下次开库重来 |
| 释放**之前**的失败、drain 那笔真落不下去 | 响亮 | 不变，照常响亮 |

宿主要注意的只有第 3 行：改了设置马上拆库（切图库）的那份，云端更新推迟到**下次开这个库**，不再是拆完 1.5 s 后。字节没丢、也不会有冲突（走的是 collection 既有的 pull-merge-push）。

## 3½. 为什么默认开、不走「默认关 + 消费方显式开」（本库规矩 ④）

- 这不是新行为，是 `dispose` 既有契约的补全：0.4.0 写的就是「dispose 后一切面拒」「drain = 等写收敛」，拆了的库上还跑定时器、还投帧是漏掉的部分。
- 默认关等于洞继续开着：它**真丢设置**（上面第 2 节），开关交给宿主 = 六家各自要记得开，正是本库要消灭的「每家各补一次」。
- 真失败的路径一条没动（drain 那笔落不下去照 warning、释放前的帧失败照 error + onError），测试里有对照钉着，所以不会把真问题藏起来。
- 只影响拆库那一刻；库活着时一个字节没变。
