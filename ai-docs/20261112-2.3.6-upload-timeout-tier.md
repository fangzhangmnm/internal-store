# 2.3.6（patch）：一次传完的上传单列一档时限，默认回到 2.3.3 的样子

> created 20261112 · 定 = 统筹 Claude Fable 5.2（小黑屋维修线；起因 = 读三维要收新同步库时的代码）· 代码 / 测试 Claude Opus 5.5（小黑屋维修线小弟）· as-of 2.3.6（没打 tag，等统筹审）
> 只影响开了请求时限（`createOneDriveProvider({ transport: { timeouts } })`）的宿主；没开的（小黑屋）一个字节不变。

## 1. 这一项为什么存在

开着请求时限的宿主，靠它保证上传卡死时不会一直卡着。三维的说明里写着：上传卡死 = 保存一直在进行 = 这期间自动保存全被跳过 = 改动只在内存里。所以「上传多久算卡死」这个数，对它是「网断死时自动保存最多被跳过多久」。

可另一头，慢网上一个 3–4 MB 带图的文件要一次传完，30 秒可能不够（上行要每秒 33–140 KB 以上），这时它会每次超时、永远传不上去。

**慢网上传得上去（时限要宽）和卡死时恢复得快（时限要窄）互相顶着**，没有一个数对所有宿主都对，所以由宿主自己定。

## 2. 改了什么

- 时限表 `GraphTimeouts` 多一个**可选**项 `upload` = 一次传完的上传（≤ 4 MB 的那一个 PUT）的时限（毫秒）。
- **不写 = 用 `meta` 那档**（推荐值 30 秒），也就是 2.3.3 及以前的行为。写了 = 一次传完的上传用写的值。
- 分块上传（> 4 MB）的每一块照旧用 `chunk`；元数据 / 列举 / 会话创建照旧 `meta`；下载照旧 `blob` / `range`。
- 推荐值表 `DEFAULT_GRAPH_TIMEOUTS` 里**不写** `upload`。现有宿主不管是直接传 `DEFAULT_GRAPH_TIMEOUTS` 还是只传一部分，都不会出类型错误。
- 没开请求时限的宿主：照旧没有任何时限。

## 3. 版本之间的差别（开着请求时限的宿主看这张表）

| 版本 | 一次传完的上传（≤ 4 MB） | `/content` 兜底下载（拿不到下载地址时） |
|---|---|---|
| 2.3.3 及以前 | `meta`（30 s） | `meta`（30 s） |
| 2.3.4、2.3.5 | `chunk`（120 s）——**默认就生效，是错的** | 整份 `blob`（15 min）/ 按范围 `range`（60 s） |
| 2.3.6 起 | **默认 `meta`（30 s）**；显式写 `upload` 就用写的值 | 整份 `blob` / 按范围 `range`（保留，见第 4 节） |

**开着请求时限的宿主不建议停留在 2.3.4 / 2.3.5**：那两版把一次传完的上传的时限默认放宽到 120 秒，等于网断死时自动保存被跳过的窗口从 30 秒变成 120 秒，而宿主没有选择。实际受影响的：收过 2.3.4 / 2.3.5 的只有小黑屋，它没开请求时限，所以至今没有宿主真的吃到。

**宿主怎么选**：
- 慢网上要能传上去大一点的单个文件（比如带图的书、几 MB 的歌）→ 写一个更宽的，比如 `upload: DEFAULT_GRAPH_TIMEOUTS.chunk`（120 秒）。
- 靠时限防卡死、自动保存会因为保存一直在进行而被跳过的（三维、画画）→ 不写（30 秒），或写一个更短的。

## 3½. 为什么 `/content` 兜底那一处默认开、不走「默认关 + 显式开」（本库规矩 ④）

2.3.4 里另一处改动：拿不到下载地址时走 Graph 的 `/content` 兜底下载，整份的用 `blob` 档、按范围的用 `range` 档（以前一律 `meta` 30 秒）。这一处保留默认开，理由：

- **同一种请求不该因为走了哪条地址而有两个时限。** 正常下载整份文件走下载地址，用的就是 `blob` 档（15 分钟）；按范围用 `range` 档（60 秒）。兜底那条路以前落在 `meta`，是按请求种类分档时漏了，不是政策选择。核过代码：`downloadItemBlob` 的两条路、`downloadItemRange` 的两条路现在各自同档。
- **宿主没有办法绕开。** 走不走兜底取决于 Graph 回不回下载地址，宿主控制不了；整份下载被 30 秒掐断时，大文件就永远下不下来。
- 一次传完的上传不一样：放宽还是收紧是真的取舍（第 1 节），所以它走开关，这一处走默认。

## 4. 测试

`test/graph-timeout-tiers.test.ts`（给 `AbortSignal.timeout` 造的信号贴上毫秒数，四档各给一个认得出的数）：
- 开着请求时限、没写 `upload`：一次传完的 PUT 带 `meta` 档。
- 写了 `upload`：一次传完的 PUT 带写的值；分块上传的那一块带 `chunk`；会话创建（元数据）带 `meta`。
- 推荐值表里没有 `upload`。
- 显式写 `upload: 60`、PUT 一直不回：60 毫秒左右被掐，抛的是没有 status 的网络错（类别 `timed-out`）——和整台测试「上传真的写进网盘之后再报超时 → 这次不算推成、仍是待传、下次续推逐字节比对自愈」注入的是同一种错，那条整台测试照旧过。
- 没开请求时限：一次传完的上传和兜底下载都不带时限。
- 全套见提交说明。对外接口：`GraphTimeouts` 多一个可选字段 `upload?: number`，别的不变。
