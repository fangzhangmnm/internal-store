# 0.15.2 — 保存与推 / 拉撞车时库自己守得住（编辑游标没人推进的洞）
> created 20260929 · by Claude Fable 5.1 · as-of 0.15.2

## 起因（WXHW 两台设备端到端测试，2026-09-29）
WXHW 为核实「冲突会不会进备份箱」搭了两台设备的端到端测试，修掉 app 层三条丢字路径之后，顺藤摸到库里一个洞。
user 2026-09-29：「同步库的一个洞 修」。

库里有一个编辑游标（`substrate.edits`），本意是回答「这段要花时间的动作进行期间，内容又变过没有」。
它要宿主自己调 `mark()` 推进。拆库之后对外只剩 `save(bytes)` 一个写入口，**没有任何宿主、也没有库自己调过 `mark()`**，游标永远停在 0。
靠它的两处保护因此是空的。

## 洞在哪（四条回归测试修之前全红，`test/edit-race.test.ts`）

| 撞车 | 修之前 | 后果 |
|---|---|---|
| 推送途中又 `save()` 了一次 | 推完 `dirtyAfter` 恒 false，dirty 被清 | 本地躺着没推的字节却显示已同步；之后的干净快进或腾空间会无备份地吃掉它 |
| 干净快进的下载途中又 `save()` 了一次 | 下载完照样覆盖本地并标干净 | 刚保存的字节没了，也不在备份箱 |
| 冲突面选了云端、下载途中又 `save()` 了一次 | 只有开头那一份进了备份箱 | 途中保存的那一份被直接覆盖 |
| 云字节正在落盘的那一下又 `save()` 了一次 | 标干净、谱系指向云端新版 | 本地最终是「旧世界 + 新改动」，下次推送 If-Match 通过，静默盖掉云端赢家 |

## 改动
- `local-head.ts`：每个文件一个保存计数 `editCount(name)`，`recordEdit` 自己涨。只在内存、只增不减。不靠宿主。
- `push.ts`：`dirtyAfter` = 全局游标变了 **或** 这个文件的保存计数变了。
- `safe-resolve.ts safePull`：开头记计数；下载、校验完之后进临界段（站在同名串行链上，和用户保存的本地写互斥）：
  1. 计数变了。静默快进作罢，本地分毫不动；用户明确选了云端则把途中那一份再备份一次，然后覆盖。
  2. 覆盖本地。
  3. 再看计数：又变了就不提交谱系，dirty 和 parent 保持 `recordEdit` 留下的样子，下次推送撞冲突面。
- 推送撞冲突后的 `resolveConflict` 已经站在串行链上，传 `inChain` 直接跑临界段（否则自己等自己）。
- `freshness.ts`：因途中保存而作罢的快进报 `dirty-skip`，不再当成「云端取不到」去报错；打开时用户选云端的那条路显式带 `forceBackup`（本来就是脏的，备份行为不变）。
- `create-store.ts`：把串行链接给 safe-resolve。

## 不变
- 对外接口（`api/*.d.ts` 里宿主用得到的面）零变化。没有新增导出、没有新的持久化字段、没有改键名。
- 没有撞车时行为逐字节照旧（第五条测试守着）。
- 全局编辑游标 `substrate.edits` 原样留着，没删：删它是接口变更，另案。

`npm test` 420 绿（415 + 5）。WXHW 收货后重跑了它的两台设备端到端测试。
