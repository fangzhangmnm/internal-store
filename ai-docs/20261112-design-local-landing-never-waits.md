## 零、要你定的三件

**先说在前面：批这份设计，等于改掉一条最早的决定的做法。** 最早那份踩坑清单的 B1（真实事故）当时定的是「用锁把（本地 + 云）包成原子」。这份设计把它收窄成「上传一趟一趟排着」，本机落盘不再包在里面。它要保的东西我认为保得住，理由和我查出来的一处漏洞在第三½节。这是你 11-12 问「会不会破坏到我们最早定的那几条安全基础」之后补的。

1. **怎么上线。** 建议：做成一个开关，默认关；小黑屋先开，用一段时间；稳了改成默认开，改成默认开之后的下一版把旧的那条路删掉。**开关只是过渡，终点是所有 app 都走新路，不留一个永久的选项让各家自己选**（user 11-12：不能靠自觉）。另一个选择是直接默认开，省掉并存，代价是画画、写歌、三维一收库就换成新路，出了毛病没有退路。
2. **保存这个动作返回什么。** 现在各 app 调一次保存，要等到上传也结束才拿到结果，所以它们的「正在存」只能挂到上传结束。两种改法：
   - 甲（第一稿的建议，现在不建议了）：保存照旧，多一个可选的「已经落到本机了」的通知。app 不用它，就还是老样子。**这是靠各 app 自觉。**
   - 乙（现在的建议）：保存返回的就是「已经落到本机了」；上传的结果从另一个口子拿。app 照最自然的写法写出来就是对的，想把「正在存」挂到上传结束反而要故意多写一步。代价：它改变了现有接口的含义，六个 app 收这一版时都要改一处，不改编译就报错。版本号怎么升由你定。
3. **这一轮做到哪。** 建议：第一刀只改「上传」和「上传撞了冲突问人」这一条路，因为每次保存都走它。改名、第一次从云端取回、清理本机副本这三样也占着队等网络，但都是你手动点的、有遮罩的动作，放第二刀。

## 一、现在是什么样，改完是什么样

**现在：** 同步库给每份文件一条队，凡是会动这份文件的事都排在这条队上，一件做完下一件才开始。这条队是好东西，它保证了两次保存不会写乱、云端的新版本不会盖掉你刚存的字。

问题在于「上传」整个排在这条队上：从取出要传的字节，到传完，到撞了冲突弹框问你，到你回答，全程占着队。所以：

- 上传在路上的那几秒到几分钟，这份文件后面的保存（包括只存本机的）都在排队，没落盘。
- 冲突框亮着等你回答的时候，同样。
- 上传卡死、或者冲突框没人回答，后面的保存就永远落不了盘。画画、写歌、三维靠「请求到点就放弃」把「永远」变成「30 秒」，这就是你说的拿氧气管搭积木。小黑屋连这个都没有。

我用真的同步库跑过：冲突框一直不回答，之后每一次只存本机的保存都不返回，磁盘上停在弹框前的那一版。

**改完：** 这条队只排「动本机磁盘」的事，每件都很短，里面不许有网络请求，不许等人。上传另排一条队，只管「同一份文件同一时刻只有一趟上传」。上传的做法变成三步：

1. 进保存的队，取出要传的那份字节，记下它是第几号，马上出来。
2. 在队外传。传多久、卡不卡、撞了冲突问你多久，都不占保存的队。这期间你打的字照常落盘。
3. 传完回来对号：盘上还是我传的那一号，就记成已同步；盘上已经是更新的，就记成「云端到了那一号，本机还有更新的没传」，下一趟接着传。

对号用的那本账是 11-10 那一版加的（当时是为了修「没传完却记成传完」），这次不用新造。库里「拉取」那一边（开文件时核对、云端有新版时换成新版、「处理…」）早就是「在队外等、回来再核对」的写法，这次是把「上传」这一边改成同样的形状。

**改完之后各 app 得到的：** 只存本机的保存永远不等网络、不等人。上传卡住只影响「传没传上去」，不影响「存没存上」。请求时限从此只是「这一趟上传等多久放弃」，取什么数都不会让字丢。

**改完也不解决的：** 各 app 自己把「正在存」挂到上传结束的那个写法，要各 app 自己改（第零节第 2 件给它们一个顺手的口子）。

## 三、要守住的东西

改的时候下面每一条都不许变薄。前七条是现有的，第八条是新的。

1. 落盘的顺序 = 保存发出的顺序（2.3.2「发出即占位」）。
2. 宣布「和云端一致」之前对号：手里推的 / 比的 / 写的那份是几号，盘上此刻是不是这一号、有没有保存还在路上（盘上账本 R1–R3，`works/disk-ledger.ts`）。
3. 采纳云端字节：脏的先留底、内容要过宿主的验真、下载途中保存过就作罢或再留一次底（0.15.2）。
4. 同一份文件同一时刻只有一趟上传（B1）。
5. 每一次上传带版本号；新建不覆盖同名（MASTER §A）。
6. 清理本机副本和本机写入互斥；脏的永不清（C2）。
7. 读盘上的字节来推的，「读」和「取号」在同一个队内步骤里（R2）。
8. **新增：保存的队里没有网络请求，没有等人。** 配一条结构守卫，见第六节。

## 三½、最早的两条决定，和这份设计的关系（2026-11-12 夜补）

user 11-12：「你想一下，这个会不会破坏到我们最早定的那几条安全基础？就是说，你先上传再落盘这个东西，是不是有什么很重要的逻辑依据了？」

**有。** 我写第一稿时以为「下一次保存等上一趟上传」只是几件事先后挂到同一条队上的副作用。翻了最早的清单（`../20260601 MyPWAPatterns/docs/20260604-potential-bugs.md`），不是：

- **B1（真实事故）**：推送之后紧接着又改、再按保存，凭空冒出「已有更新版本」。原因 = 上一趟上传还在路上，下一趟拿的是旧版本号。决策原文：「串行化 push——`_cloudPushing` 锁把 (本地+云) 包成原子；`saveAndPush` await 在途 push；忙时 spinner，按钮 disable。」
- **B2（「同步层最微妙的 race」）**：一次按键落在上传的那两三百毫秒里；上传成功，代码把「没传」清掉，可这次按键不在传上去的内容里，静默丢了。对策原文：「PUT 后重读 IDB，只有内容仍与所推一致才清 dirty。」

这两条从一开始就是往两个方向拉的：B1 的做法是把本机和云包成一个整体，上传时不让本机变；B2 的做法是承认上传时本机会变，传完回来核对。今天的库两样都有。**这份设计让 B2 那一样来承重，把 B1 收窄成「上传一趟一趟排着」。**

B1 要保的是：下一趟上传开始时，上一趟已经落定，手里的版本号是新的。改完之后靠这两样保：

1. 传队：同一份文件的上传一趟一趟来，下一趟的取样在上一趟落定之后。
2. 上一趟落定时本机还有更新的没传 → `head.onPushed(name, etag, dirtyAfter = true)` 把基准和「这些改动派生自哪一版」都换成刚传上去的那一版（`works/local-head.ts` 141–153 行，注释原话「剩余编辑派生自刚推上去的版本」）。这一段我读过，今天就是这么写的。

**「包成原子」白送的那条性质，和靠着它的地方。** 包成原子之后，上传的过程中盘上不会变，云端那一头也只有这一趟上传在动。改完之后这条性质没有了。库里靠着它的地方必须一处一处找出来。我已经找到的：

- **加密、解密、换口令（隐私红线）。** 它们在写队里先换本机、再换云端（`create-store.ts` `encSwap`）。今天它们会等在途的上传。按第一稿，上传不占写队，加密就可能和一趟还在路上的**明文**上传叠着：加密换完云端之后，那趟明文才落地，云端留着明文而人以为已经加密了；或者那趟明文先落地、加密的云端那一步撞版本号，之后人在冲突面里选了云端，本机又变回明文。**所以它们必须先拿传队。**
- **清理本机副本。** 干净的文件被强制重传的途中清掉本机副本，回来对号时盘上是「没了」。2.3.2 审稿时补过「没了不算待传」，但更稳妥的是它也先拿传队。
- **「处理…」和干净文件的快进。** 第一稿已经写了。

由此定一条总的规矩，替代第一稿里零散的几句：

- **写队** = 盘上的字节正在被写。只有短的、纯本机的步骤。
- **传队** = 这份文件和云端的关系正在被改。上传、加密转换、改名、第一次取回、清理本机副本、「处理…」、换成云端那一版，都先拿它。
- **只有「保存」这一个动作只拿写队。** 这正是这份设计要的全部效果：保存不等别的；别的照旧互相等。

**施工前必须先做的一步（新增）：** 把 `doPush` 和它所有调用方里「跨过一次 await 之后还在用之前读到的盘上状态或谱系状态」的地方列成表，逐条写清改完之后凭什么还成立。我这次是读代码时碰巧想到加密的，不能保证没有第二处。这张表给 user 看过再开第一刀。

**顺带的一个好处：** 关页面时的最后一次保存，今天如果正好排在一趟上传后面，页面死之前落不了盘。改完它不排在上传后面。

## 三¾、请求时限的来历（2026-11-12 夜补）

user 11-12：「这个三十秒是不是有其深意的？就是说是不是它是某种强制用户用某种逻辑写，而不是靠用户自觉？因为我前面说了，我们不能依靠用户自觉来保证安全性和秩序……还是说，其实最一开始的时候，我们实际上是没有超时的，就他宁愿会一直卡下去。我怀疑最一开始是这样的。」

查的是本仓的提交记录和发版说明：

| 什么时候 | 发生了什么 | 出处 |
|---|---|---|
| 2026-10-15 之前 | 没有任何请求时限，卡住就一直卡着 | — |
| 2026-10-15，0.17.1 | 加了请求时限，默认就开：元数据 / 列举 / 会话 30 秒、一块 5 MiB 的上传 120 秒、取一段 60 秒、整份下载 15 分钟。起因原文：「iOS 锁屏 / 切后台后在途的 fetch 常常永远挂着 → **消费方的「正在存」锁、在途计数全挂死**（KudsRocket 10-15「多锁几次，全卡死了，手动存档都不行了」）」 | 提交 6741b51；`20261015-0.17.1-timeouts-chunk-resume-precommit-etag.md` |
| 2026-10-15 当天，0.17.2 | user：「我其实非常怕把家族文件的那些 app 开始丢画」→ 三条政策「123同意」→ 全部改成显式开关，**默认回到没有超时** | 提交 6889fdb；`20261015-0.17.2-transport-opt-in.md` |
| 之后 | KudsRocket（10-15）、画画（10-21）、三维（10-25）、写歌（11-09）各自打开。小黑屋、读书没开，至今是最初的样子 | 各仓 `app-store.ts` |

所以：

- **最一开始没有超时。** user 的怀疑是对的。
- **30 秒没有强制任何东西。** 它是一个默认关着的可选项里的一个数；发版说明里没有它的理由，也没有记 user 定过它；那一版是 AI 写的。4 MB 以内一次传完的上传没有被单独列出来，是没人想到它才落进了 30 秒。
- **这个功能出生那天写明的用途，就是去解开宿主那把卡住的「正在存」的锁。** user 11-12 晚批评的「拿库的保命机制当积木」不是哪个 app 后来才学坏的，是请求时限在库里被设计出来时就带着的，然后三个 app 抄了同一段说明。

这份设计改完之后，请求时限回到它该有的位置：只决定一趟卡死的上传等多久放弃，取什么数都不影响字丢不丢。到那时它该不该还是一张各家能改的表，另说。

## 四、改法

**两条队。** 每个名字两条：

- **写队**：现在这条，只留动本机磁盘的短步骤。
- **传队**：新的，同样是一个名字一条 promise 链，只用来排上传。拿队的顺序永远是先传队、后写队；写队里的步骤不许去等传队。这样不会互相等死。

**上传（`doPush`）改成：**

- 进传队。
- 取样（进写队，短）：`encode()` 取字节、`seal.sealForWrite` 封装（2.3.2 要求封装在队里做，照旧）、号 `g` = 保存自己的号，或者读盘时的 `ledger.disk(name)`、**同一步里**读谱系算出 If-Match（字节和它派生自哪一版要在同一刻取，中间不许插进别的写）。出写队。
- 需要重捕谱系时（2.2.1）问云端在队外做，问回来 `markSeen`、重算 If-Match；手里的字节还是取样的那份。
- 上传、重试之间的退避：队外。
- 成功：同步的一步里 `pendingAfter(name, g)` 对号，`head.onPushed(name, etag, dirtyAfter)`。这一步今天就有，今天因为占着队所以几乎总是「没变」；改完之后它成了承重的那一下。
- 撞 412 / 409：自愈（下载云端和**取样的那份**逐字节比）在队外；比上了，同步的一步里对号、认领。比不上，问人，队外。
  - 云端覆盖本地：`safePull`，它的提交段自己进写队（今天因为上传占着队，传的是 `inChain: true` 直接跑；改完传 `false`）。它本来就处理「下载途中又保存过」。
  - 本地覆盖云端：云端拷贝留底加上传，队外；传的还是取样的那份（和今天一样），传完对号，盘上有更新的就留着待传。
  - 取消：什么都不动。
- 出传队。

**对号和记账这一小步为什么不用进写队：** 它是同步的，中间没有 await，JavaScript 里不会被别的步骤插进来；`settled` / `pendingAfter` 看的正是「有没有保存发出了还没落盘」。今天开文件和「处理…」里的自愈就是这么做的。要进写队的只有读盘和写盘。

**跟着改的调用方：** 批量补传、离线补传队列、重新上传、「处理…」里的本地覆盖云端，现在是自己先进写队再调推送；改成直接调推送，由推送去拿传队和取样。它们开头的「还脏不脏」检查挪到拿到传队之后。

**「处理…」整个也排传队。** 它今天在队外问云端、问人，这没问题；但改完之后它可能和一趟在飞的上传同时对同一份文件做决定（比如上传撞了冲突正在问人，人又从书库点了「处理…」选云端覆盖本地）。规矩：同一份文件同一时刻只有一个「同步决定」在进行，所以「处理…」从头到尾拿着传队。它等的只是别的上传，不占写队。

**谁拿传队，见第三½节的总规矩。** 加密、解密、换口令、清理本机副本、第一次取回，第一刀里做法照旧（照旧在写队里做完自己的事），只加一处：先拿传队。

**改名这一刀不动，但要和新的上传对上：** 改名今天占着两个名字的写队、在里面调推送。第一刀里它照旧，只加两处：先拿两个名字的传队（保证不和在飞的上传叠着），再拿写队；它在队里调推送时带一个「我已经在写队里」的记号，推送的取样就直接做、不再进队（今天 `safePull` 的 `inChain` 是同一个办法）。改名因此还是会等在飞的上传，和今天一样，不变差。

**收尾：** `dispose` 的「等所有队尾做完」要把传队也算上（`substrate.ts` 的 `drain`）。

## 五、每一种叠着的情况

| 情况 | 今天 | 改完 |
|---|---|---|
| 上传在路上，又保存了一次（只存本机） | 保存等上传结束才落盘 | 立刻落盘；上传回来对号对不上 → 记「云端到了旧的那一号，仍待传」→ 下一趟传新的 |
| 上传在路上，又保存了一次（存并传） | 同上，然后再排一趟上传 | 立刻落盘；它的上传排在传队里，前一趟结束后接着传 |
| 冲突框亮着，人去忙别的了 | 这份文件的保存全排着 | 保存照常落盘；只有这份文件的下一趟上传在等 |
| 冲突框永远没人答 | 之后的字永远落不了盘 | 之后的字都在盘上；这份文件不再上传，待传计数如实显示 |
| 上传卡死 | 同上，直到请求到点 | 保存照常落盘；这份文件的上传卡到请求到点或页面刷新 |
| 上传成功的那一下，正好有一次保存发出 | 2.3.2 已修（对号） | 同一套对号 |
| 人选了云端覆盖本地，下载途中又保存了 | 那一份再留一次底，然后覆盖（0.15.2） | 一样 |
| 人选了本地覆盖云端，问的时候又保存了 | 传的是问之前的那份，传完仍待传 | 一样 |
| 上传在路上，人点了清理本机副本 | 脏的被拒 | 一样（脏的被拒）；干净的强制重传途中被清掉 → 回来对号时盘上是「没了」，按「没了不算待传」记（2.3.2 审稿补的那条） |
| 上传在路上，开文件做新鲜度检查 | 检查在队外，本来就并行 | 一样；云端正好是我们刚传上去的那一版时，走已有的自愈（比字节、认领） |
| 上传在路上，云端快进（干净的文件） | 脏的不快进；干净的强制重传时可能并行 | 一样。建议顺手加一条：传队被占着时快进作罢，按「本来就脏」处理，少一种并行 |
| 两个标签页 | 各记各的基准，带版本号 | 不变（两条队都只在本页内存里） |

## 六、怎么证明它是对的

1. **留底探针转绿。** `test/repro/20261112-write-lane-held-while-waiting.probe.ts` 第一段现在退出码是 1，改完要是 0，然后搬进正式测试。
2. **现有的全套测试原样过**（645 条），开关关着和开着各跑一遍。
3. **叠着的时序，逐条写**：第五节每一行一条测试，开关开着时断言「改完」那一列，关着时断言「今天」那一列。F-188 那个复现脚本的五种时序在开关开着时也要全过。
4. **随机调度的性质测试。** 假云盘的每个请求都卡在一个可以由测试放行的闸上；测试随机穿插：发出保存、放行或掐断一次上传、回答或不回答冲突框、让别的设备改云端、点清理。每一步之后查：
   - 每一份落了盘的保存，要么云端有它，要么待传计数里算着它。
   - 盘上的字节 = 最后一次发出并落盘的保存（或者人选了云端覆盖本地之后的云端那版，而且之前的每一份都在留底里）。
   - 没有哪一次只存本机的保存在等网络或等人（给它一个很短的期限，过期就红）。
   - 同一份文件在飞的上传不超过一趟。
   - 每一次「宣布一致」发生时，盘上那一号 = 推上去的那一号。
5. **结构守卫：**
   - 写队的每一个调用点登记在一张表里；回调体里不许出现对云端的调用、对 `ui` 的调用、`fetch`。多一处、少一处、挪了都红。（和 2.3.2 的 `declare-synced-guard` 同一个做法。）
   - `declare-synced-guard` 的表跟着改：每一处「宣布一致」写清它的号从哪来、对号在哪一步。
6. **宿主层：** 小黑屋的端到端里「冲突面亮着时又来一张问人的面」那一类场景加一条「冲突框亮着不回答，接着打字，刷新页面，字都在」。三维有一个真会话加真库的探针（自动保存撞上续推），Catsup统筹说可以拿来当回归。
7. **放行之前**，审的人自己写攻击脚本去撞，不用施工方的测试。

## 七、怎么上线

- 库仓规矩 ①：行为变更做成显式开关、默认关。所以第零节第 1 件我的建议是开关。名字施工时定。
- 分三刀，每刀单独能发：
  1. 只加传队，上传同时占着两条队。行为和今天一样，全套测试原样过。这一刀是纯搬动。
  2. 开关开着时，上传在取样之后让出写队；冲突的问人挪到写队外；批量补传、离线补传、重新上传、「处理…」跟着改。第五、六节的测试在这一刀交。
  3. 第零节第 2 件：按 user 选的甲或乙做。选乙的话这一刀是改接口的含义，要另出一份接口对照（现状和提案各一份，家规的 API 仪式），六个 app 各自收的时候改。
- 小黑屋先开开关（它没有请求时限，也没有独立的崩溃影子，最需要这个）。
- 第二刀之后另起一轮：改名、第一次取回、清理本机副本、加密转换，也改成「网络在队外」。
- 版本号：每刀一个补丁号。第零节第 2 件是给接口加东西，按家规也只升补丁号，但要你点头。

## 八、对各 app 的要求（库改完之后）

- 「正在存」只表示「还没落到本机」。上传在后面自己走，状态另外显示。
- 不靠请求时限保证任何逻辑正确。时限可以开，作用只是让一趟卡死的上传早点放弃、好排下一趟。
- 冲突框没人答、上传卡住，都不该影响打字和落盘。各 app 自己的端到端里各加一条这样的场景。
- 这三条和三维今晚打算做的方向一致（Catsup统筹：正在存只管本机落盘）。画画、写歌碰到时对一遍。

## 九、拿不准的和没查的

- 加密、解密、换口令在队里做的云端那一步，我只读了开头几行，没读完。第二轮做之前要读。
- 「上传在路上、云端快进」加不加那条「传队被占着就作罢」，我倾向加，但它会让「强制重传干净的文件」期间多一次「没能核对」。施工时看测试再定，定了告诉 user。
- 排在传队里的每一趟上传手里都拿着自己取样的那份字节。连着存并传很多次、而第一趟卡住时，内存里会攒着好几份。今天也是这样（它们排在同一条队上）。以后可以做「排队的上传轮到时发现盘上已经更新就不传了」，这次不做。
- 两个标签页同时开同一份文件的那几种情况，我没有重新推一遍。两条队都只在本页内存里，跨页靠的还是版本号，这次没有动它。11-10 那份审计里「两个标签页互相盖的检查从没接上」仍然开着。
- 这份设计没有在代码上试过。第一刀做完如果发现哪条队的调用点和这里写的对不上，以代码为准，回来改这份稿子。

## 附、三维清点之后向库要的三个接口（2026-11-12 夜，Catsup统筹；都不在这份设计的第一刀里，做不做归 user）

三维清点出九处「靠库的保命机制才成立」的地方（三维仓提交 f97130a1 的 `ai-docs/20261112-sync-session-facts-and-borrowed-safety.md`），都在三维自己那一层改。其中三处是因为库没给正经的口子，宿主只好从别处猜：

1. **取消一次核对或拉取。** 人点了「先离线用」，那次下载停不下来，在后台接着跑，跑完可能把字节换掉；三维为了不让它换，在库问「本机脏不脏」的回调里夹带了「闸已经放弃了」。库现在的接口：`open` / `pullIfClean` 只有「和逃生赛跑」，没有真的取消。我的看法：该给。和这份设计是同一个方向（每个等云端的时刻都有出口，而且出口是干净的）。
2. **库的动作返回「本机副本现在是哪一版」。** 宿主要判断眼前的画布和本机副本还是不是同一条线，现在只能从冲突面的回调里看人选了什么。库现在的接口：`open` / `pullIfClean` 的结果里只有来源和状态。我的看法：该给，但给什么要想清楚——把盘上账本的号直接露出去，它就成了对外的承诺。
3. **续签失败的原因做成正式的字段。** 三维、小黑屋的闸门现在都是读库的一行诊断文字（`[auth] silent token renewal failed (…): name=… code=… sub=…`，`base/providers/auth.ts` 131 行）来分辨「登录过期」还是「没回应」。这是拿诊断文字当接口，库改一个字宿主就读不出来。我的看法：该给，最小、最不容易出错的一个。
